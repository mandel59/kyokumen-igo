# Rust / WASM と JavaScript の速度比較（2026-10-21）

同じ 300 局面を使った Node.js 上の計測では、既存 Rust 実装を WASM にしたものが、既存 JS 実装に比べて着手計算で約 **8.3 倍**、手順からの局面復元・転送込みで約 **10.8 倍**速くなりました。異なる Node.js プロセスで 2 回実行し、ほぼ同じ比率を得ています。

この測定時点では比較用のアダプタを使い、アプリへの WASM 導入は行っていませんでした。その後のアプリへの組み込みは [アプリ用 WASM AI](WASM.md) を参照してください。

## 環境と比較条件

| 項目 | 条件 |
| --- | --- |
| OS / CPU | Windows x64 / AMD Ryzen 7 3700X |
| Node.js / V8 | v26.7.0 / 14.6.202.34-node.28 |
| Rust | rustc 1.99.0 (b940084d7 2026-09-28) |
| WASM target | `wasm32-unknown-unknown` |
| 最適化 | `opt-level=3`、LTO、codegen-units=1、panic=abort |
| 並列化 | JS / WASM ともに単一スレッド |
| 局面 | 既存の [parity.json](parity.json) 全 300 局面。6 種類の盤で各 50 局面 |
| 評価の重み | 両方とも採用済みの tuned |
| 乱数加点 | 両方とも 0 に固定 |
| ウォームアップ | 各測定方式で全 300 局面をそれぞれ 10 周 |
| 計測 | 各盤・各実装で、50 局面 × 4 周を 1 標本として 21 標本 |
| 集計値 | 各標本の平均 ms/手を求め、その 21 標本の中央値 |
| 実行順 | 標本ごとに JS 先 / WASM 先を交代 |

JS、WASM の保持済み局面、WASM の手順から復元した局面のすべてで、300 / 300 局面の選択手が fixture と一致しました。盤の隣接関係・勢力範囲は両方でキャッシュし、計測中に使い回しています。

## 着手計算だけの比較

盤面・履歴をそれぞれの実装に準備済みの状態で、`chooseMove` / `choose_move` を呼んでいます。WASM 側は 1 手ごとに JS から WASM を 1 回呼ぶ時間を含みます。局面の変更は行いません。

以下の表は 2 回目の実行結果です。

| 盤 | JS（ms/手） | WASM（ms/手） | 速度比 JS / WASM |
| --- | ---: | ---: | ---: |
| 球面 n=3（56 点） | 0.0818 | 0.0135 | 6.08 倍 |
| 球面 n=4（98 点） | 0.2071 | 0.0235 | 8.82 倍 |
| 球面 n=5（152 点） | 0.4263 | 0.0438 | 9.72 倍 |
| トーラス 7×7 | 0.0706 | 0.0122 | 5.77 倍 |
| トーラス 9×9 | 0.1657 | 0.0225 | 7.35 倍 |
| トーラス 11×11 | 0.2838 | 0.0339 | 8.37 倍 |

各盤の中央値 × 50 局面を足した時間の比は、1 回目 **8.274 倍**、2 回目 **8.265 倍**でした。個々の速度比の単純平均ではありません。

## 手順からの局面復元・転送込み

こちらは、各局面の全手順から新しく対局状態を構築し、着手を選ぶまでの時間です。盤の隣接関係は引き続きキャッシュしています。

WASM 側は手順を `Int32Array` から WASM の線形メモリへコピーし、その手順を Rust で再生してから着手を選びます。転送用バッファは事前確保し、毎回のコピーと Rust 内部の局面構築は計測に含めています。JS 側も新しい `Game` に全手順を再生してから着手を選びます。手順の合法性確認は両方で行います。

| 盤 | JS（ms/手） | WASM（ms/手） | 速度比 JS / WASM |
| --- | ---: | ---: | ---: |
| 球面 n=3（56 点） | 0.2943 | 0.0369 | 7.97 倍 |
| 球面 n=4（98 点） | 0.6242 | 0.0560 | 11.15 倍 |
| 球面 n=5（152 点） | 1.3473 | 0.1082 | 12.46 倍 |
| トーラス 7×7 | 0.2365 | 0.0317 | 7.47 倍 |
| トーラス 9×9 | 0.5857 | 0.0599 | 9.78 倍 |
| トーラス 11×11 | 1.1277 | 0.0985 | 11.45 倍 |

各盤を同数ずつ処理した時間の比は、1 回目 **10.777 倍**、2 回目 **10.779 倍**でした。

これは JSON の変換や Worker 間メッセージングを含みません。現行の `ai-worker.js` は JSON 化した保存履歴から復元するため、この測定方式とは異なります。アプリ全体の応答時間を直接測った結果ではありません。

## WASM モジュールの初期化

生成された WASM は **131,726 bytes（約 128.6 KiB）**でした。各プロセスで最初に読み込んだときの時間です。

| 処理 | 1 回目 | 2 回目 |
| --- | ---: | ---: |
| ローカルファイル読み込み | 6.920 ms | 0.207 ms |
| `WebAssembly.compile` | 1.428 ms | 0.978 ms |
| `WebAssembly.instantiate` | 0.098 ms | 0.078 ms |

ネットワークからのダウンロード時間は含みません。ファイル読み込みは OS のキャッシュなどの影響を受けます。300 局面の準備・JS と WASM の一致検証はこの表に含まず、着手計算の計測より前に行っています。

## 結果の解釈

この結果は、現在の 2 つの実装をそのまま比較したものです。WASM の性能と、Rust 移植時の処理方法の変更の両方を含みます。

JS 版は石の連や呼吸点の探索で `Set` や配列を作り、スーパーコウ判定で盤面全体を文字列にします。Rust 版は探索用配列を使い回し、Zobrist hash を差分更新します。手順の再生時も、JS 版は各手の盤面スナップショットを保存しますが、Rust 版の履歴は着手位置だけです。これらを揃えた「言語だけの比較」ではありません。

今回の最大盤でも JS 版の着手計算は約 0.43 ms、WASM 版は約 0.044 ms です。大量の対局や、今後 1 手あたりに多くの局面を調べる探索を追加する場合に、この差を活用できます。

同じ局面を繰り返すウォームアップ後のスループット測定なので、初回の 1 手、GC による個別の遅延、実ブラウザ、スマートフォン、Worker への導入後の応答時間は別途確認が必要です。選択手の一致検証も、あらゆる局面でのルール上の同値性を証明するものではありません。

## 再実行

リポジトリ直下から実行します。PowerShell では各行の成功を確認してから次へ進んでください。

```sh
rustup target add wasm32-unknown-unknown
node -e "require('node:fs').mkdirSync('tools/ai-tuner/target/wasm-bench',{recursive:true})"
rustc --edition 2021 --target wasm32-unknown-unknown --crate-type cdylib -C opt-level=3 -C lto=fat -C codegen-units=1 -C panic=abort -A dead_code tools/ai-tuner/bench-wasm.rs -o tools/ai-tuner/target/wasm-bench/engine.wasm
node tools/ai-tuner/bench-wasm.mjs
```

[bench-wasm.rs](bench-wasm.rs) は既存の Rust エンジンを読み込む計測専用アダプタです。[bench-wasm.mjs](bench-wasm.mjs) が一致確認と時間計測を行い、結果を `target/wasm-bench/results.json` に書きます。

今回の 2 回分の全標本と実装・fixture の SHA-256 は [wasm-node-results.json](experiments/2026-10-21/wasm-node-results.json) に保存しています。コンパイル済み WASM は `target/` 内に生成し、Git の管理対象にはしていません。
