# アプリ用 WASM AI

AI の着手計算を Rust / WASM に移し、Web Worker 内で実行します。配信物は `dist/ai-engine.wasm`（現ビルドで 57,461 bytes）です。

## WASM に移す範囲

| 処理 | 担当 |
| --- | --- |
| AI 候補手の合法性、取り、連・呼吸点、スーパーコウの確認 | Rust / WASM |
| AI の勢力評価・採点・最大 4 手の探索・着手選択 | Rust / WASM |
| 実際に対局へ着手を適用する最終検証 | JS の `Game` |
| プレイヤーの入力、待った、終局・得点表示 | JS |
| 保存復元、棋譜リンク、設定、盤面描画 | JS |

計算量の多い AI 評価を移すことで、保存形式や操作・描画のインターフェースを変えずに高速化します。Rust は調整ツールと同じ [ai.rs](src/ai.rs)、[board.rs](src/board.rs)、[rng.rs](src/rng.rs) を使います。現在は [search.rs](src/search.rs) の最大 4 手の候補限定探索を使います。従来の一手評価も、比較実験・一致確認と JS フォールバックのために維持します。初版は [探索 AI の評価](SEARCH-AI.md)、現行係数と盤別採用は [チューニング記録](SEARCH-TUNING.md) を参照してください。

## データとライフサイクル

1. UI は盤種・サイズ・コミ・全着手履歴を Worker へ送ります。着手履歴は `Int32Array` で、交点番号、パスは `-1` です。各手の盤面スナップショットは送りません。転送するバッファは UI の対局状態とは別に作ります。
2. Worker は WASM を 1 度読み込み、ABI バージョンと、一手評価版の全 14 項目の重みを JS と照合します。探索係数と配信物の一致は、ビルド照合と代表対局の native / WASM テストで確認します。
3. WASM は履歴を合法手として再生し、スーパーコウを含む状態を復元します。候補を絞った最大 4 手の alpha-beta 探索で着手を選びます。乱数は JS から渡す seed を使い、ルート候補の順位に少量のゆらぎを加えます。
4. UI は回答を現在の `Game` で検証してから着手します。

Worker は手番をまたいで再利用します。WASM 内では現在の盤の隣接関係・勢力範囲・探索用配列と入力バッファを再利用し、盤種やサイズを変えると以前の盤を解放します。対局状態は各リクエストの履歴から作り直すため、待ったや保存復元との同期用に別の永続状態を持ちません。

新しい対局、待った、棋譜表示への切り替えなどの取消しでは Worker を終了し、リクエスト ID を更新して古い回答を無視します。通常の回答では終了しません。計算は次のイベントループですぐに依頼し、AI の手番全体が最低 400 ms になるよう、早く返った回答だけ残り時間を待って反映します。計算自体が 400 ms 以上かかった場合は追加で待ちません。この待機も取消しの対象です。

## フォールバック

WASM 非対応、取得失敗、破損したモジュール、ABI / 重みの不一致、WASM の実行失敗では Worker 内の JS 版を使います。Worker 自体を使えない場合や回答が JS のルール検証に失敗した場合は、UI 側の JS 版へ切り替えます。

WASM の初期化にはバイト列からの `WebAssembly.instantiate` を使い、静的ホストの Content-Type が `application/octet-stream` でも動作します。外部パッケージやネットワーク上の AI サービスは不要です。

## ビルドと配信

配布済みの `dist/` にはコンパイル済み WASM を含めます。アプリを起動するだけなら Rust は不要で、従来どおり `dist/` 全体を静的配信します。

Rust の AI や盤・ルール、WASM のアダプタを変更した場合は、リポジトリ直下から再生成します。

```sh
rustup target add wasm32-unknown-unknown
node tools/ai-tuner/build-wasm.mjs
node wasm-tests.mjs
```

ビルドは rustc 1.99.0、`opt-level=3`、LTO、codegen-units=1、panic=abort、strip=symbols で確認しています。ビルドスクリプトはカレントディレクトリに依存しません。変更後のソースと配布バイナリの一致は、同じツールチェーンで次のように確認できます。

```sh
node tools/ai-tuner/build-wasm.mjs --check
```

## 検証

- `search-tests.mjs`：代表対局で native と WASM の探索結果を照合し、JS のルール・得点で再検証します。
- `wasm-tests.mjs`：配布する実際の WASM と JS で 300 局面の選択手を照合します。取り・スーパーコウ、待った後の分岐、パス・終局、乱数、入力の検証も確認します。実際の Worker ハンドラを Worker thread 上で動かし、WASM の再利用、404・破損・非対応時の JS 切り替えを検証します。
- `ui-tests.mjs`：Worker の再利用、転送した履歴、待った・新しい対局による取消し、古い回答・エラーの無視、不正な回答からの JS 切り替えを確認します。
- 既存のエンジン、保存復元、棋譜、描画、回転・投影などのテストも通しています。
- ヘッドレス Edge 155.0.4283.62 では、HTTP 配信した実アプリで WASM の使用、2 手番で Worker / WASM 取得が各 1 回であること、待った・再読み込み後の対局、スーパーコウ履歴の復元を確認しました。WASM を 404 にした場合の JS 継続と、Content-Type が `application/octet-stream` の場合も確認しています。

高速化の事前測定は [WASM-BENCHMARK.md](WASM-BENCHMARK.md) を参照してください。そちらの約 8.3 倍はウォームアップ後の着手計算の比較で、アプリの描画・保存・Worker 起動を含めた応答時間の倍率ではありません。
